# **Abstract**

This RFC proposes the **Intent Compilation Pipeline (ICP)**, a deterministic software engineering framework designed specifically for AI-assisted engineering workflows.

The core premise is that modern conversational AI development introduces severe non-deterministic failure modes:

* Loss of Intent  
* Context Drift  
* Specification Drift  
* Test Drift  
* Code Drift

To eliminate these risks, human domain intent must be represented exclusively through executable, version-controlled artifacts. Under this model, Large Language Models (LLMs) are treated not as collaborative design partners or autonomous agents, but as stateless code compilation units operating on formally defined inputs and constraints.

# **Problem Statement**

Most AI-assisted development workflows follow an informal, conversational pattern:**Human Intent** → Natural Language Prompt → **LLM** → Code → **Tests**

This architecture exhibits several structural weaknesses:

1. **Intent exists primarily in chat history**, making it ephemeral and unversioned.  
2. **Requirements are not executable or verifiable**, leading to subtle semantic misunderstandings.  
3. **Test quality is unverifiable**, as AI agents often generate tests tailored to validate their own (potentially flawed) implementations.  
4. **Conversations become hidden system state**, degrading over time due to context window limits.

As systems evolve, correctness becomes increasingly dependent on undocumented, non-reproducible conversational context—a phenomenon defined as **Intent Leakage** or **Loss of Intent**.

# **Design Goals**

The Intent Compilation Pipeline aims to establish:

* **Deterministic implementation behavior** from human specification to output code.  
* **Reproducible AI execution** by providing stateless, explicit contexts.  
* **Objective correctness measurement** via automated, zero-trust verification.  
* **Aggressive detection of intent leakage** before deployment.  
* **Complete bidirectional traceability** from domain business rules down to source code.

# **Core Principle & Axioms**

Software development in an AI-assisted environment is treated strictly as a compilation process:Business Intent → Executable Specification → **Red Tests** → Source Code → **Running System**

Each stage represents a progressively more formal, machine-readable representation of the previous layer.

## **Core Axioms**

* **Axiom 1:** Intent is the primary artifact.  
* **Axiom 2:** AI cannot own intent.  
* **Axiom 3:** Only executable artifacts may carry state.  
* **Axiom 4:** Passing tests prove correctness.  
* **Axiom 5:** Killed mutants prove intent preservation.

# **Intent Compilation Pipeline Architecture**

| Layer | Component | Ownership & Description |
| :---- | :---- | :---- |
| **Layer 0** | Domain Invariants | **Human-Owned** • Timeless business rules and constraints |
| **Layer 1** | Executable Specifications | **Human-Owned** • BDD / Gherkin feature files |
| **Layer 2** | Red Tests | **Human-Owned** • Executable bindings & failing unit tests |
| **Layer 3** | Green Implementation | **AI-Generated** • Minimal passing source code |

## **Layer 0: Domain Invariants**

* **Definition:** Fundamental, technology-agnostic domain rules and invariants.  
* **Characteristics:** Implementation-independent, scenario-independent, timeless.  
* **Examples:**  
  * Money values cannot be negative.  
  * Order totals cannot be less than zero.  
  * Promo code identifiers must be unique.  
* **Purpose:** Prevents semantic drift before behavioral scenarios are written.

## **Layer 1: Executable Specifications**

* **Definition:** Business intent expressed through concrete executable examples using Gherkin syntax (`.feature` files).  
* **Technologies:** Reqnroll, Cucumber, Gherkin.  
* **Example:**

Scenario: Valid promo code application

  Given cart total is 1000

  When customer enters promo code "SAVE10"

  Then total should be 900

* **Purpose:** Translates high-level domain invariants into observable behaviors.

## **Layer 2: Red Tests**

* **Definition:** Executable test bindings and unit test suites that validate the specifications.  
* **Mandate:** Strictly written by human engineers. Never generated by AI from raw natural language requirements.  
* **Purpose:** Serves as the authoritative, non-negotiable verification contract.

## **Layer 3: Green Implementation**

* **Definition:** The actual production source code.  
* **Inputs to AI:**  
  1. Executable Specification (Layer 1\)  
  2. Concrete Types and Interfaces  
  3. Failing Test Suite (Layer 2\)  
* **Output:** Minimal passing implementation code.  
* **Mandate:** The AI is granted zero design authority beyond satisfying the failing tests.

# **Verification & Quality Gates**

The framework introduces a Dual Quality Gate mechanism to separate implementation correctness from test resilience.**AI Code Generation** → **Gate 1:** Correctness *(All Tests Green?)* → **Gate 2:** Resilience *(100% Mutants Killed?)* → **Definition of Done**

## **Gate 1: Correctness (Unit & BDD Verification)**

* **Question:** Does the generated implementation satisfy the specification?  
* **Mechanism:** Automated test suite execution (Reqnroll / xUnit / NUnit).  
* **Criterion:** All unit and BDD acceptance tests must pass (GREEN).

## **Gate 2: Resilience (Mutation Testing as Intent Leakage Detection)**

* **Question:** Do the tests genuinely enforce the intended business rules?  
* **Mechanism:** Automated Mutation Testing (e.g., Stryker.NET).  
* **Criterion:** 100% Mutation Score (or all admitted mutants killed).

## **Scientific Interpretation**

Traditional unit tests verify implementation correctness (*Code satisfies test*). Mutation testing verifies specification and test completeness (*Tests enforce business intent*).

A surviving mutant indicates that code can be altered without breaking tests. In the ICP framework, this is classified not as a software bug, but as Intent Leakage between the specification and test layers.

# **Human vs. AI Authority Model**

| Responsibility Domain | Human Engineer | AI Assistant |
| :---- | :---- | :---- |
| **Domain Invariants & Business Intent** | Owner | Excluded |
| **BDD Specifications (`.feature`)** | Owner | Excluded |
| **Red Tests & Verification Contracts** | Owner | Excluded |
| **Refactoring Approval** | Owner | Excluded |
| **Green Implementation Code** | Reviewer | Generator |
| **Implementation Alternatives** | Evaluator | Proposer |
| **Mechanical Refactor Proposals** | Reviewer | Proposer |

# **Definition of Done (DoD)**

A feature or change request is considered fully compiled and complete only when:

1. **Specifications Pass:** All BDD Gherkin scenarios execute successfully.  
2. **Unit Tests Pass:** All underlying unit/integration tests pass.  
3. **Mutation Score \= 100%:** Mutation testing confirms zero surviving mutants in modified logic.  
4. **E2E / System Verification Pass:** High-level acceptance criteria are satisfied.

At this point, the translation path **Intent → Spec → Tests → Implementation** is formally verified to be free of semantic leakage.

# **Conclusion**

The Intent Compilation Pipeline redefines AI-assisted development as a deterministic, formal transformation process. Rather than asking *"Can the AI generate this feature?"*, the framework asks **"Can the human domain intent survive compilation into executable software without loss of fidelity?"**

By combining human-owned BDD specifications with automated mutation testing as a final Quality Gate, ICP provides a rigorous engineering framework for safely leveraging AI code generation at enterprise scale.
